📦 SFT 数据构建

对话格式、Chat Template、损失掩码——SFT 数据到底长什么样？

📖 快速复习：上一章讲了什么

  • SFT 和 Pre-train 架构相同，区别在数据格式和损失范围
  • SFT 只对 assistant 的回答算 loss，用户输入部分用 -100 跳过
  • 学习率从 5 × 10⁻⁴ 降到 1 × 10⁻⁵（小 50 倍）
  • 损失计算的区别完全在 labels 的构造上，模型本身不感知

🧱 数据格式：从纯文本到对话

预训练数据是这样的（纯文本，一行一条）：

# pretrain_t2t_mini.jsonl
{"text": "在很久很久以前，有一座山，山上有一座庙..."}
{"text": "量子力学是描述微观粒子的物理学理论..."}

简单粗暴：一条文本就是一个样本。

模型的任务：看完前半段，预测后半段。

SFT 数据长这样（对话格式）：

# sft_t2t_mini.jsonl
{"conversations": [
  {"role": "user",
   "content": "今天天气怎么样？"},
  {"role": "assistant",
   "content": "今天天气晴朗，温度20°C..."}
]}

每条数据是一个对话列表，每条消息有 role 和 content。

模型的任务：看完整个对话历史，能正确预测 assistant 的回答。

🔄 数据流：一条 SFT 样本的一生

① raw JSON → ② 预处理 → ③ Chat Template → ④ Tokenize → ⑤ 生成 Labels → ⑥ 训练

步骤 ① ~ ②：原始 JSON → 预处理

# SFTDataset.__getitem__()
sample = self.samples[index]
conversations = pre_processing_chat(sample['conversations'])
prompt = self.create_chat_prompt(conversations)
input_ids = tokenizer(prompt).input_ids[:max_length]
labels = self.generate_labels(input_ids)

预处理 pre_processing_chat() 做了两件事：

  1. 如果有 tool use 数据，完整保留
  2. 以 20% 的概率给对话加上 system prompt（"你是一个有用的AI助手"等）

为什么要随机加？让模型学会有时有 system prompt，有时没有，增加泛化能力。

步骤 ③：Chat Template——把对话变成文本

模型看不懂 JSON，它只能看 token。所以我们需要把对话"渲染"成一段文本：

# create_chat_prompt()
def create_chat_prompt(self, conversations):
  messages = []
  for message in conversations:
    messages.append(dict(message))
  return self.tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=False
  )

apply_chat_template() 是 tokenizer 自带的方法，它根据模型的 chat template 把对话"渲染"成一段文本。

对于 MiniMind，渲染后的结果类似：

<bos><user>\n今天天气怎么样？\n</user>\n<assistant>\n今天天气晴朗。\n</assistant>\n<eos>

步骤 ④：Tokenize——文本变数字

把上一步的文本变成 token ID 序列：

# tokenize 结果（简化示意）
input_ids = [
  BOS, # 1
  USER, 今, 天, 天, 气, 怎, 么, 样, ?, USER_END,
  ASST, 今, 天, 天, 气, 晴, 朗, ., ASST_END,
  EOS, PAD, PAD, ...
]

对话中的特殊标记（如 <user>、<assistant>）在 tokenizer 的词表中都有对应的 ID。

这些特殊标记也是"token"，模型需要学会它们的含义。

步骤 ⑤：生成 Labels——"掩码"的艺术

这一步是 SFT 数据构建的精髓。来看 generate_labels() 的实现：

def generate_labels(self, input_ids):
  labels = [-100] * len(input_ids)
  i = 0
  while i < len(input_ids):
    # 找到 assistant 的开始标记
    if input_ids[i:i+len(self.bos_id)] == self.bos_id:
      start = i + len(self.bos_id)
      end = start
      while end < len(input_ids):
        # 直到遇到 assistant 的结束标记
        if input_ids[end:end+len(self.eos_id)] == self.eos_id:
          break
        end += 1
      # assistant 部分保留 label
      for j in range(start, min(end + len(self.eos_id), max_length)):
        labels[j] = input_ids[j]
    i = end + len(self.eos_id)
  return labels

这个函数做了什么？

它在 input_ids 中找到所有 assistant 回答的位置，然后把 label 设为实际的 token ID。

其余位置（user 输入 + padding）都设为 -100。

-100 是 PyTorch CrossEntropyLoss 的特殊忽略值——在这些位置不计算梯度。

注意：这里匹配的是 self.bos_id，它是 tokenizer(f'{bos_token}assistant\n') 的结果，用来定位 assistant 回答的起始位置。

让我们用可视化的方式看看 labels 长什么样：

input_ids: BOS <user> 今天天气怎么样? </user> <assistant> 今天晴朗 </assistant> EOS PADPAD
labels: -100 -100 -100-100-100-100-100-100-100-100 -100 今天晴朗 </assistant> EOS -100-100
🟦 蓝色 = 用户输入（不计算 loss） | 🟩 绿色 = 模型回答（计算 loss） | ⬜ 灰色 = padding（忽略）

🎨 多轮对话的处理

上面的例子只有一轮（一问一答）。但真实 SFT 数据经常是多轮对话：

# 多轮对话示例
{"conversations": [
  {"role": "user",
   "content": "1+1等于几？"},
  {"role": "assistant",
   "content": "等于2"},
  {"role": "user",
   "content": "那2+2呢？"},
  {"role": "assistant",
   "content": "等于4"}
]}

有趣的是，generate_labels() 使用 while 循环，可以自动处理多轮对话！

它会在 input_ids 中找到所有的 <assistant>...</assistant> 区间，把它们都设为有效的 label。

这样，模型在每一轮都要学会正确回答，而不是只学最后一轮。

💡 多轮对话的 loss 变化：随着对话进行，上下文越来越长，模型需要"记住"前面的对话历史。 这相当于在训练模型的长程记忆能力和上下文关联能力。

📊 数据统计：Pretrain vs SFT

维度 🔧 Pre-train 数据 💬 SFT 数据
数据量~10GB+~几 MB 到几百 MB
数据格式纯文本（text 字段）对话列表（conversations 字段）
数据来源互联网爬取人工标注 / 蒸馏
质量要求低（量大就行）高（每个回答都要有用）
序列长度较短（340）较长（768+）

📝 本章小结

SFT 数据构建的核心要点：

  1. 对话格式：每条数据是一个 role/content 列表
  2. Chat Template：用 tokenizer.apply_chat_template() 把对话渲染成文本
  3. 损失掩码：labels 中只保留 assistant 回答位置，其余设为 -100
  4. 多轮支持：generate_labels() 自动找到所有 assistant 区间
  5. 随机 system prompt：以 20% 概率添加，增加泛化能力
  6. 数据量少但精：SFT 数据不需要很大，但质量必须高
🤔 思考题：SFT 数据中，如果某条对话有 3 轮（user→assistant→user→assistant→user→assistant）， 模型是只学最后一轮的 loss，还是三轮的 loss 都学？为什么？

💡 点击查看答案

三轮都学！ generate_labels() 会找到所有 <assistant>...</assistant> 区间。 这是因为模型需要学会在任何一轮中都给出好的回答，而不仅仅是最后一轮。 如果只学最后一轮，中间轮次的错误回答就没有梯度信号去纠正了。

打个比方：如果老师只批改期末考试的最后一题，那期中考试做错了也没人知道——学生永远不会改进。
