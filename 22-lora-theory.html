🎛️ LoRA 微调

Low-Rank Adaptation——"用一张小卡片，微调整个大模型"

📖 前情回顾

  • 全量微调（Full SFT）更新所有参数，显存占用巨大
  • RLHF 篇的 DPO/PPO/GRPO 也都是全量微调
  • 但大多数时候，我们只是想要模型学会一个新技能，而不是重新学习语言

💡 核心问题：全量微调真的太"重"了

假设我们要让一个 7B 参数的模型学会做数学题。全量微调（Full Fine-Tuning）的问题是：

  • 显存爆炸：需要存储所有参数的梯度 + 优化器状态，一个 7B 模型用 AdamW 训练需要约 60GB 显存
  • 全盘重学：每次微调都更新全部参数，而新任务只需要修改很小一部分知识
  • 灾难性遗忘：学新任务的过程中，模型可能忘记之前学到的通用知识

🔬 LoRA 的核心思想

🎯 LoRA 假设：模型参数的更新量 ΔW 是低秩的，即
rank(ΔW) << min(d, k) （d 和 k 是原始权重矩阵的维度）

所以：ΔW = B · A 其中 B ∈ ℝd×r, A ∈ ℝr×k, r << d, k

💡 一个比喻： 预训练模型是一个博学的教授（W），已经掌握了各种知识。 LoRA 就像给教授一张小抄（B·A），教授还是那个教授，只是他看问题时会顺便瞄一眼小抄。 训练小抄比重新培训教授便宜得多！

🧮 参数量的"魔法"

以 MiniMind 的 d = 768 为例，对比全量微调和 LoRA 的参数量：

方法一个 Linear 层8 层 Transformer 的 QKV节省比例
全量微调768 × 768 = 589,8248 × 3 × 589,824 = 14,155,776—
LoRA (r=16)768×16 + 16×768 = 24,5768 × 3 × 24,576 = 589,824↓ 96%
LoRA (r=8)768×8 + 8×768 = 12,2888 × 3 × 12,288 = 294,912↓ 98%
LoRA (r=4)768×4 + 4×768 = 6,1448 × 3 × 6,144 = 147,456↓ 99%

用 r=8 的 LoRA，可训练参数只有全量微调的 2%！这意味着：

  • 显存占用从 60GB（7B 全量）降到 ~16GB（LoRA）
  • 单张消费级显卡（RTX 3090/4090）就能跑
  • 训练时间缩短 10 倍以上

🧩 MiniMind 的 LoRA 实现

1. LoRA 模块定义

class LoRA(nn.Module): def __init__(self, in_features, out_features, rank): super().__init__() self.rank = rank # A: d→r（降维） self.A = nn.Linear( in_features, rank, bias=False ) # B: r→d（升维） self.B = nn.Linear( rank, out_features, bias=False ) # A 高斯初始化 self.A.weight.data.normal_( mean=0.0, std=0.02) # B 全零初始化（初始无影响） self.B.weight.data.zero_() def forward(self, x): return self.B(self.A(x))

两个关键设计：

1. B 全零初始化

训练开始时，B·A = 0，所以 W + B·A = W，模型输出不变。

这意味着 LoRA 初始时不会影响模型性能，训练过程中的梯度会慢慢地让 B·A 学会需要更新的方向。

2. A 高斯初始化

如果 A 也是全零，梯度永远为零，模型永远不会学习。

2. apply_lora：把 LoRA "贴"到模型上

def apply_lora(model, rank=16): for name, module in model.named_modules(): if isinstance(module, nn.Linear) \ and module.in_features == module.out_features: lora = LoRA(module.in_features, module.out_features, rank=rank) # 把 lora 挂载在 module 上 setattr(module, "lora", lora) original_forward = module.forward # Hook forward：输出 = 原始 + LoRA def forward_with_lora( x, layer1=original_forward, layer2=lora): return layer1(x) + layer2(x) module.forward = forward_with_lora

这段代码做了什么？

  1. 遍历模型所有子模块
  2. 找到 方阵 Linear 层（in_features == out_features）
  3. 为每个方阵层创建一个 LoRA 模块
  4. 修改 forward 函数：h = Wx + BAx

为什么只对方阵层？

因为 Attention 的 Q/K/V/O（还有 FFN 的 gate/down/up）都是方阵。这也意味着 LM Head（vocab×hidden）不会被 LoRA 修改。

3. 保存 & 加载 LoRA 权重

def save_lora(model, path): raw_model = getattr( model, '_orig_mod', model ) state_dict = {} for name, module in \ raw_model.named_modules(): if hasattr(module, 'lora'): lora_state = { f'{name}.lora.{k}': v.cpu().half() for k, v in module.lora.state_dict().items() } state_dict.update(lora_state) torch.save(state_dict, path) def load_lora(model, path): state_dict = torch.load( path, map_location=model.device ) for name, module in \ model.named_modules(): if hasattr(module, 'lora'): lora_state = { k.replace(f'{name}.lora.', ''): v for k, v in state_dict.items() if f'{name}.lora.' in k } module.lora.load_state_dict(lora_state)

保存的是 LoRA 权重，不是整个模型。

一个典型的 LoRA checkpoint 只有几 MB（全量微调的几十分之一）！

加载时也是只加载 LoRA 部分——原始权重已经在模型中了。

这就是 LoRA 的便利性：你可以为不同任务训练不同的LoRA 卡片，然后在推理时切换加载。

4. merge_lora：合并回原始权重

def merge_lora(model, lora_path, save_path): # 加载 LoRA 权重 load_lora(model, lora_path) raw_model = getattr( model, '_orig_mod', model ) # 提取原始权重 state_dict = { k: v.cpu().half() for k, v in raw_model.state_dict().items() if '.lora.' not in k } # 把 LoRA 合并到原始权重 for name, module in \ raw_model.named_modules(): if isinstance(module, nn.Linear) \ and '.lora.' not in name: state_dict[f'{name}.weight'] = \ module.weight.data.clone().cpu().half() if hasattr(module, 'lora'): state_dict[f'{name}.weight'] += \ (module.lora.B.weight.data @ module.lora.A.weight.data ).cpu().half() torch.save(state_dict, save_path)

merge 的作用：

将训练好的 B·A 直接加到原始权重 W 上：

W' = W + B·A

合并后的模型不依赖 LoRA 模块，推理速度和原始模型一样快。

什么时候需要 merge？

  • 部署到生产环境（减少额外开销）
  • 作为基座做下一步微调
  • 需要极致推理速度时

🎯 LoRA 与全量微调的对比

维度Full SFTLoRA
可训练参数量全部（100%）约 0.1%~2%
需要存储梯度所有参数仅 LoRA 参数
优化器状态全量（Adam: 2x 参数）仅 LoRA 参数
显存占用（7B）~60GB~16GB
训练速度慢快 2-4 倍
效果理论上限最高近似全量（r 足够时）
多任务能力每个任务一套完整权重基座 + 多张 LoRA 卡片

📝 LoRA 在 SFT 和 RLHF 中的应用

在实际项目中，LoRA 最常见的用法是作为 SFT 和 DPO 的轻量替代方案：

🎯 LoRA + SFT

用 SFT 数据训练 LoRA，
只需 16GB 显存

🎯 LoRA + DPO

在 LoRA 基础上做 DPO，
2 个 LoRA 模型即可

🎯 LoRA + PPO

Actor + Critic 都用 LoRA，
4 个模型也能跑得动

⚠️ 注意：MiniMind 的 LoRA 实现是"手动挡"——它通过 Hook forward 手动修改前向传播。 在实际生产中更推荐使用 peft（HuggingFace 的 Parameter-Efficient Fine-Tuning 库）， 它提供了更完善的 LoRA 实现，包括 LoraConfig、get_peft_model 等。

📝 本章小结

  1. LoRA 的核心假设：模型参数的更新量 ΔW 是低秩的
  2. 公式：W + ΔW = W + B·A，B 是 d×r，A 是 r×k，r 通常取 8~64
  3. 初始化：A 高斯初始化，B 全零初始化——训练开始时等效于原始模型
  4. 参数量减少 98%+：7B 模型训练只需要 ~16GB 显存
  5. MiniMind 实现：LoRA 类 + apply_lora + save/load/merge
  6. apply_lora：只对方阵 Linear 层应用 LoRA，通过 Hook forward 修改计算图
  7. merge 操作：训练完后可以将 B·A 合并回 W，推理零开销
🤔 思考题：为什么 apply_lora 只选择 in_features == out_features 的 Linear 层？如果 我们也对非方阵层（比如 embedding 层）应用 LoRA，会有什么问题？

💡 点击查看答案

理论上可以对任何 Linear 层应用 LoRA，包括非方阵层。但实践中通常只在方阵层（QKVO、FFN 的 gate/down/up）做，原因有：

  1. Embedding 层嵌入维度太大（vocab_size × hidden_size），LoRA 的参数量会很大，失去效率优势
  2. LM Head 通常 tied embedding（权重共享），改 embedding 会同时影响输入输出，容易出问题
  3. 经验表明：Attention 的 Q/K/V 和 FFN 的 down-projection 是 LoRA 最有效的位置。这些层存储了模型的核心"知识"，更新它们就能很好地适配下游任务

实际上，MiniMind 代码中因为 modules 遍历时 filter 条件是 module.in_features == module.out_features， 所以只选中了方阵层——这无意中符合了 LoRA 的最佳实践！
