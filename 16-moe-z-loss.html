🛡️ Z-Loss 正则项

梯度稳定性问题——Z-Loss 如何防止 logits 无限放大

📖 前情回顾

上一章我们解决了"专家坍塌"问题（用 Load Balancing Loss）。但 MoE 还有一个隐患——Router 的 logits 可能会无限变大，导致训练不稳定。

⚠️ 另一个问题：Logits 爆炸

视频里说："门控网络会把这个 logits 无限放大……经过指数运算时，很容易溢出。"

为什么 Router 的 logits 会变大？

  • Router 输出的是 N 个专家分数（logits）
  • 训练过程中，为了"更确定地选择"某个专家，Router 倾向于把选中专家的 logits 推得很大
  • 但 softmax 中 ex 的指数增长非常快！
  • 如果 logits = 20，e20 ≈ 4.8 × 108——爆炸了！
⚠️ 后果：logits 爆炸 → softmax 概率分布极度尖锐（几乎 one-hot）→ 反向传播梯度爆炸 → Loss 变成 NaN → 训练失败。

🛠️ 解决方案：Z-Loss

Z-Loss 是一个正则项，直接惩罚 Router 的 logits 的幅度：

📐 Lz = (log Σi=1N exp(gi))²

其中 gi 是 Router 对第 i 个专家的原始 logits。

💡 直觉：log Σ exp(gᵢ) 近似等于 max(gᵢ)（当某个 logits 明显大于其他时）。所以 Z-Loss 就是在惩罚"最大的 logits"的平方。logits 越大，惩罚越大。

🔍 Z-Loss vs Load Balancing Loss

维度Load Balancing LossZ-Loss
解决的问题专家坍塌（分配不均衡）Logits 爆炸（数值不稳定）
惩罚对象Token 分配比例 + Router 概率Router logits 的幅度
公式N · Σ(f_i · p_i)(log Σ exp(gᵢ))²
效果让每个专家分到差不多多的 token让 Router logits 保持在合理的数值范围
⚠️ 注意：MiniMind 的 MOEFeedForward 中没有直接实现 Z-Loss（因为它使用较小的默认配置，logits 爆炸问题不严重）。但在大规模 MoE（如 Mixtral 8×7B）中，Z-Loss 是标配。你可以自己加上！

🧪 如果你要自己实现 Z-Loss

在 MOEFeedForward.forward() 中可以这样加：

# 在 forward 开头获取原始 logits
gate_logits = self.gate(x_flat)

# 计算 Z-Loss
z_loss = torch.logsumexp(gate_logits, dim=-1)
z_loss = (z_loss ** 2).mean()

# … 后面继续做 softmax 和 topk …
scores = F.softmax(gate_logits, dim=-1)

# 累加到 aux_loss
self.aux_loss += self.config.z_loss_coef * z_loss

关键代码：

torch.logsumexp：计算 log Σ exp(gᵢ)，数值稳定的实现。

.mean()：对所有 token 的 Z-Loss 取平均。

这个 loss 会通过反向传播告诉 Router："别太自信！把你的 logits 降下来！"

📝 本章小结

  1. Z-Loss 解决 logits 爆炸：防止 Router 的输出无限放大
  2. 公式：(log Σ exp(gᵢ))²——惩罚"总 logits"的幅度
  3. 和 Load Balancing Loss 互补：一个管分配均衡，一个管数值稳定
  4. 视频总结："Z-Loss 约束门控的 logits 大小，缓解数值溢出和梯度爆炸"
